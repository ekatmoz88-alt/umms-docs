# Локальное хранение дел и досье в клиенте УММС

> Публичный обзор архитектуры по анализу выбранного исходного файла C#. Это не полная спецификация базы данных и не описание серверной реализации.

## Контекст программно-аппаратного АРМ

В предоставленном фрагменте руководства АРМ описано как комплекс для оформления документов, состоящий из Мобильной и Стационарной станций. В составе аппаратной части прямо упоминаются:

- компьютер и устройства ввода (в частности, клавиатура и манипулятор);
- монитор для вывода информации;
- система защиты электропитания с постоянно действующим двойным преобразованием;
- цветное лазерное многофункциональное устройство.

Описание МФУ в исходном фрагменте обрывается, поэтому дополнительные функции устройства здесь не перечисляются.

Класс `CaseProvider` относится к пространству имён `DbStationary`, что связывает его с программной частью Стационарной станции. Этот вывод основан на исходном коде; полный состав аппаратных компонентов и их модели требуют отдельной проверки по руководству и спецификациям оборудования.

## Назначение компонента

Класс `DbStationary.Providers.CaseProvider` реализует операции доступа к локальному хранилищу Стационарной станции. В исходном коде используются SQLite, модели пространства имён `Common.Data.Models.Umms` и модели `DbStationary.Models`.

Компонент отвечает за сохранение и загрузку дел, досье и связанных с ними сведений. Вызовы SOAP-сервиса в показанном классе отсутствуют: его ответственность ограничена локальным хранилищем.

## Основные операции

| Метод | Назначение по исходному коду |
|---|---|
| `AddCase` | Создаёт дело и сохраняет входящие в него досье |
| `AddDossier` | Добавляет досье к существующему делу |
| `AddDocumnet` | Добавляет документ в досье (имя метода сохранено как в исходнике) |
| `UpdateDossierScenario` | Обновляет номер и статус сценария |
| `UpdateDossierScenarioXml` | Сохраняет XML-представление сценария |
| `LoadCases` | Загружает дела, досье и связанные данные |

## Логическая структура данных

SQL-запросы и операции маппинга в классе показывают следующие сущности:

| Таблица | Данные, используемые компонентом |
|---|---|
| `Cases` | Идентификатор дела, комментарии, даты экспорта и импорта, статус, GUID |
| `Dossier` | Ссылка на дело, комментарии, номер и статус сценария, XML сценария |
| `Person` | Идентификатор UMMS, имя, даты рождения и смерти, место рождения и другие атрибуты |
| `DocumentXml` | XML документа, идентификатор документа, дата создания |
| `AddressXml` | XML адреса, идентификатор адреса, дата создания |
| `CaseXml` | XML сведений о деле, дата создания и признак `Declarent` |

Связи, явно используемые в SQL-запросах:

- `Cases.ID` → `Dossier.CaseID`;
- `Dossier.ID` → `Person.DossierID`;
- `Dossier.ID` → `DocumentXml.DossierID`;
- `Dossier.ID` → `AddressXml.DossierID`;
- `Dossier.ID` → `CaseXml.DossierID`.

Сведения о документах, адресах и связанных делах сериализуются в XML перед сохранением. При загрузке XML десериализуется обратно в объектные модели.

## Сценарий сохранения

1. Создаётся запись в `Cases`.
2. Для каждого досье создаётся запись в `Dossier`.
3. Сохраняются атрибуты лица в `Person`.
4. Документы, адреса и сведения о связанных делах сериализуются в XML и сохраняются в отдельных таблицах.
5. Сохраняются идентификаторы созданных записей в соответствующих моделях.
6. Операции добавления выполняются внутри SQLite-транзакций, после завершения которых вызывается `Commit`.

## Сценарий загрузки

1. Загружается список дел с сортировкой по дате импорта.
2. Для каждого дела загружается список досье.
3. Читается XML сценария, если он присутствует.
4. Загружаются сведения о лице.
5. Загружаются XML документов и адресов, затем выполняется десериализация.
6. Загружаются связанные дела двух категорий, различаемых значением поля `Declarent`.

Если список дел пуст, метод `LoadCases` возвращает `null`. Исключения при загрузке записываются через `UmmsLogger` и повторно выбрасываются вызывающему коду.

## Связь с SOAP-интерфейсом

Названия моделей `UmmsPersonModel`, `UmmsDocumentModel`, `UmmsAddressModel`, `UmmsCaseModel` и поле `UmmsID` согласуются с предметными данными UMMS SOAP API: лица, документы, адреса и дела.

Однако `CaseProvider` сам по себе не доказывает, какой компонент вызывает SOAP-операции и каким способом данные поступают в локальную базу. Для установления этого потока необходимо исследовать вызывающий код и компоненты импорта/синхронизации.

## Границы анализа и вопросы для проверки

Обзор основан на одном классе. Он не подтверждает полную схему БД, ограничения таблиц, индексы, внешние ключи, механизм обмена между Мобильной и Стационарной станциями или серверную бизнес-логику.

При дальнейшем техническом аудите следует проверить:

- реализацию `SQLiteCommandEx` и способ выбора соединения для запросов `last_insert_rowid()`;
- схему таблицы `CaseXml` и соответствие полей SQL-запросов фактической структуре;
- поведение вызывающего кода при возврате `null` из `LoadCases`;
- обработку ошибок сериализации и десериализации;
- транзакционные границы и согласованность обновления связанных моделей.

## Краткий архитектурный вывод

`CaseProvider` — слой доступа к локальным данным Стационарной станции. Он сохраняет структуру дела и досье в SQLite, хранит часть вложенных данных в XML и восстанавливает объектную модель при чтении. Его роль — локальное хранение, а не реализация SOAP API или процесса обмена между станциями.
